# 设备端方案

设备端是**审批的呈现与决策面**：显示 hub 推来的请求，把人的意思变成 `accept` / `reject`。
它不理解命令语义，也不做策略判断——那些在 hub 和客户端适配器里。

一个方案 = 一套自成一体的实现。**固件、硬件设计、方案专属文档放在同一个目录下**，
因为它们是一起变的：改引脚要同时动原理图和固件，分开放必然分叉
（v3 那版原理图和实测通过的固件分叉过，起因就是两边分着改）。

## 现有与计划

| 方案 | 目录 | 状态 | 定位 |
|---|---|---|---|
| C3 矩阵键盘 | [`c3-keypad/`](c3-keypad/) | 面包板实测通过 | 哑终端，最强的带外保证 |
| S3 触摸屏 | [`s3-touch/`](s3-touch/) | 未开始 | 软键盘，界面丰富 |
| 手机 App | [`mobile/`](mobile/) | 未开始 | 不在工位也能批 |

## 选型：三个方案不是等价替换

**保证强度递减，便利性递增。** 完整推导见 [`../docs/threat-model.md`](../docs/threat-model.md)，
这里只给结论：

```
c3-keypad   哑终端、可选有线、无通用计算能力、agent 完全碰不到   ← 保证最强
s3-touch    固件复杂、联网、触摸面可被界面重排
mobile      通用联网设备、要过第三方推送、共享密钥认证不够用     ← 最便利
```

选哪个取决于你在防什么：

- 防 **agent 判断失误或手滑** —— 三个都够用，选顺手的
- 防 **本机被入侵后的审批伪造** —— 只有 c3-keypad 有意义，另两个的信任根都在联网软件里
- 想 **离席也能批** —— 只有 mobile 能做到，代价写在威胁模型里

不要把三个方案的裁决当成同一强度记进审计。协议里的
`enforcement` 与 `confirm` 字段就是为此存在的，见 [`../protocol/README.md`](../protocol/README.md)。

## 加一个新方案要做什么

1. 建 `devices/<name>/`，固件/App 源码、硬件设计、方案文档都放进去
2. 实现 [`../protocol/`](../protocol/) 的设备侧契约：收 `request`、回 `decision`、上报 `hello` 声明能力
3. **`hello` 里如实声明能力档位**，别声明做不到的东西——hub 靠它决定要不要代为排版、
   以及这台设备的裁决该以什么强度入账
4. 实现强确认（`confirm`）。做不到就在 `hello` 里说做不到，hub 会拒绝把高危请求推给它
5. 写方案 README：接线/构建/刷机怎么做，已知坑是什么

hub 侧不需要为新方案改代码。如果需要改，说明协议漏了东西，先回去改协议。

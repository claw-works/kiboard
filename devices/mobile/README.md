# 方案 C：手机 App（未开始）

Android / iOS 上的审批端。**目录先占位，代码还没写。**

## 为什么它该是第二个做的

两个理由：

1. **不用等硬件**，写完就能验
2. **它是纯自渲染设备**，会强迫协议彻底语义化。如果 App 能只靠 `request` / `decision`
   工作，说明抽象是对的；如果发现少字段，那是协议的问题，趁只有两个设备时改最便宜

换句话说，它的第一价值是**协议的试纸**，第二价值才是"离席也能批"。

## 它换来什么，代价是什么

唯一能做到**不在工位也能批**的方案。代价是保证强度最低，三处：

- **通用联网设备**。手机上装着几十个 App，攻击面和一块只会扫矩阵的单片机不是一个量级
- **第三方推送在链路里**。要及时收到审批请求就得走 APNs / FCM，多一跳不受控的中间人。
  推送内容里**不能带命令原文**（会落在第三方日志和锁屏上），只能带"有请求待批"+ id，
  正文由 App 拉取
- **认证必须升级**。现在 `/device` 用的是共享 token（`kiboard-dev-token` 这种），
  一台手机丢了就等于审批权丢了。手机方案上线前必须先做按设备的独立凭据 + 可吊销

完整推导见 [`../../docs/threat-model.md`](../../docs/threat-model.md)。

## 待决问题

- **跨端还是双原生**。倾向跨端（一份代码两个平台），但生物识别和推送要各写一遍原生
- **强确认怎么表达**。物理键的"按住 900ms"在手机上有更好的等价物：**生物识别**
  （Face ID / 指纹）。但注意——那是"确认了本人"，不是"确认了按住时长"，
  两者保证的东西不同，审计里要如实记成哪一种
- **hub 怎么暴露**。手机不在内网时要能连上 hub。别为此把 hub 裸暴露到公网，
  优先考虑内网穿透或 VPN；直接开公网端口的话，认证升级是前置条件而不是后续优化
- **离线怎么办**。手机连不上 hub 时不能有任何"默认放行"，客户端侧的 fail-closed 照旧

## 协议侧的要求

`hello` 里声明：

- `render: "self"` —— 自己排版，hub 不代劳
- `confirm` 支持哪些方式（`hold` / `biometric` / 无），hub 据此决定敢不敢把高危请求推给它
- `enforcement` 档位如实填 —— 手机上的裁决和物理键的裁决不是同一强度，
  审计要能区分，否则复盘事故时会得出错误结论

required-to-display 的约束同样适用：**逐字原文必须显示**。手机屏幕大、界面漂亮，
最容易犯的错就是只显示一句友好的 summary 让人一键批准——那正是协议要防的事。
